# Root Cause — DBG-1016 Coordinate Picker

## Finding

The user clarified that they press the lower-right current-location button; the initial map-tap hypothesis is excluded from the reported path.

**Confirmed source behavior:** the current-location button requests a fused location and asks the controller to move the picker camera when a usable fix arrives. Its `onLocationUpdated` callback is empty, so pressing the button does not itself write new coordinates to the form. The coordinates are returned only when Confirm is subsequently tapped; Confirm samples the map camera center.

The FAB is a camera recenter action. The selected waypoint marker is rendered from the session snapshot and is not repositioned by the FAB; the fixed crosshair remains at the screen center. Thus, if “marker” means the existing waypoint pin or crosshair, its not moving is expected before confirmation. If it means the map camera or Google Maps' blue current-location dot, that is a separate failure to recenter/acquire a location.

This explains the missing form coordinate if the expectation was that the location button itself commits the location. It also means the map will not move if permission is denied or no usable fix is returned. Since GPS acquisition is asynchronous and Confirm remains enabled while it is pending, confirming before camera movement can return the previous center.

**Additional source-confirmed no-op window:** `onCreate()` makes the picker overlay/FAB visible before the asynchronous `getMapAsync()` callback sets `googleMap`. `MyLocationController.enableMyLocationAndMove()` immediately returns if its map provider is null. The FAB remains enabled during this window, so a tap before `onMapReady()` is silently dropped: no GPS request, no camera movement, and no new coordinate. This explains both symptoms if the button was tapped immediately after opening the picker.

**Leading shared-controller cause:** the controller can keep a cached location at the original map center instead of moving to the user's newer location. It accepts any cached fix up to five minutes old and animates to it. It then calls `getCurrentLocation()` but that API is not guaranteed to return a fresh fix: Google Play services documents that it may return a recent cached fix or compute a fresh one, and may return `null` on timeout. The app adopts the result only when its timestamp is newer and its accuracy improves by at least 10 m (`LocationFixQualityPolicy.shouldUseRefinement`). The policy ignores coordinate displacement, so an equal-timestamp cached result, a timeout/null result, or a newer fix with equal/worse accuracy can leave the camera at the accepted cache. Once a cache was accepted, a null/failed/rejected refinement does not invoke the unavailable-location callback, so no toast appears. This branch matches the confirmed unchanged map and absent toast if the accepted cache was at/near the picker’s original center. It remains unproven for the incident: the picker has no instrumentation, the fix values at the tap were not captured, and the main map had successfully recentered with the same controller less than a minute earlier, which weakens the fit. Google documents the cache/fresh-fix behavior in [FusedLocationProviderClient](https://developers.google.com/android/reference/com/google/android/gms/location/FusedLocationProviderClient).

**Regression history:** commit `4086c3461af84a013ab65cc3567a8343be54e33e` (`fix(debug-0917-location): use cached location first`, authored 2026-09-18) introduced the cached-first/refinement policy and replaced the picker’s previous direct `lastLocation` camera move with the shared controller. This establishes when the relevant behavior entered the picker implementation. It does not by itself prove this user’s run hit the stale-cache branch.

**Updated incident assessment:** the user confirmed permission was granted, the picker map was fully loaded before tapping, no unavailable-location message appeared, they waited several minutes, and the emulator location was changed after login to a position clearly different from saved point A. In the picker, the blue current-location dot appeared near the fixed crosshair, and the user specifically confirmed it was near original point A; the underlying map remained at A. In source, `MyLocationController.enableMyLocationAndMove()` is the only code that enables `map.isMyLocationEnabled`, after obtaining a non-null picker `GoogleMap`. This establishes that the FAB handler ran and a map object was available; a missed tap and null-map race are excluded. It does not identify why the camera remained at A: the controller accepts a usable cached fix and may silently retain it if the follow-up is null, same-timestamp, or rejected; however, the successful main-map recenter using the same controller less than a minute earlier argues against a provider-wide stale state. The user confirms the live three-tab half-height import sheet was used. Recent Access and Search work; Nearby alone shows the explicit `無資料` empty state and does not update the view to B. In current source, that state is produced only when `ApiResult.Success` is received and `response.data` is null or empty. API errors produce `載入失敗…`; thrown exceptions produce `發生錯誤…`; location timeout has its own message. Read-only logs from the task emulator `emulator-5554` now directly confirm one no-query Recent request returned HTTP 200, followed by two Nearby requests with `lng`/`lat` that each returned HTTP 200 and `success=true, data=[]`. Query coordinates were redacted in log output and response records were reduced to counts, so no point data or location was exposed. Therefore the immediate cause of the Nearby empty list is a successful empty API response, at **99% confidence**. Why the backend returns an empty list for those exact query coordinates remains unknown. Static source confirms Nearby sends `GET /api/v1/node/closestNodeDetails?lng=...&lat=...` with Bearer auth to the same endpoint used by Recent without query; success responses are passed directly to the list and map without client-side filtering. The repository unit test verifies method overload, argument order, and Bearer header using a fake service; it does not verify real GPS coordinates or backend results.

Nearby obtains the query coordinate from `hostLastLatLng` first (passed in the form intent from the main map's last-known location), and also requests a fused location. If the host coordinate is present, `tryLoadNearbyFromHost()` immediately shows that marker and queries from that coordinate before refinement completes. `requestCurrentGpsAndLoadNearby()` then prefers that host value over fused `lastLocation`; a later update can replace it only if it is newer and at least 10 m more accurate. The policy compares timestamps and accuracy, not geographic displacement. A form holding A can therefore continue to show/query A after device location becomes B if no live refinement arrives or if its accuracy improvement is below 10 m.

### Shared location-policy trace — 2026-10-16

The standalone `MapPointPickerActivity` FAB shares `LocationFixQualityPolicy` through `MyLocationController`. On a location-button tap, the controller first accepts a cached fix if it is no older than five minutes and immediately animates the camera to that fix. It then requests a high-accuracy current fix, but only animates again when the candidate timestamp is newer and its accuracy improves by at least 10 m. If a cached A is accepted and a fresh B has similar reported accuracy, the controller silently keeps the camera at A; because an accepted cached fix exists, this rejection also does not invoke the unavailable-location toast.
