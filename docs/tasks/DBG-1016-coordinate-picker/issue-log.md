# Issue Log — DBG-1016 Coordinate Picker

## ISS-DBG-1016-MAP-001 — Current-location button does not recenter to the new location

- Task: `DBG-1016`
- Phase found: `verification` (reported after feat-1015 implementation)
- Category: `implementation_regression` candidate; runtime branch not instrumented
- Priority: `P2`
- Related acceptance criteria: `feat-1015` AC-003 (nearby GPS/location marker and camera behavior); `ISS-DBG-1016-COORD-002` may affect AC-005 if its selection path is confirmed.
- Status: investigating
- Impact: A user may be unable to select or obtain a changed coordinate through the picker.
- Reported symptoms:
  - After pressing the lower-right current-location button, the map does not move to the changed location.
  - The map marker does not move to the user's new current location.
  - No new coordinate is obtained.
- Additional user report: after changing a coordinate from point A to point B, navigating through `ImportExistingWaypointActivity.kt` → `GutterFormActivity.kt` → `AddGutterBottomSheet.kt` and back shows A coordinates again. The exact UI/path and return action are not yet identified.
- User clarified the trigger is the lower-right current-location button.
- Source evidence: The button requests a fused location and moves the picker camera only when a usable fix arrives. Its location callback does not commit form coordinates. Confirm returns the current camera target and is the only step that sends coordinates to the form. Confirm remains enabled while location acquisition is pending.
- Additional source finding: the picker makes the FAB visible before `onMapReady()`. A tap in that window reaches a controller that returns silently when the map provider is null.
- Additional candidate cause: a recent cached fix is used immediately, but a newer, geographically displaced refinement is discarded unless reported accuracy improves by at least 10 m. The policy does not compare geographic displacement.
- Source-level match: an accepted cached fix causes a camera move, and a null, failed, same-timestamp, or rejected follow-up result produces no unavailable-location toast because that callback is only invoked when no cached fix was accepted. Google Play services permits `getCurrentLocation()` to return a cached fix or `null` on timeout. If the accepted cache matched the picker's original center, this branch matches the unchanged map plus absent toast; the actual fix values at the user's tap are not recorded.
- User confirmed permission is granted, the picker map was fully loaded before tapping, no unavailable-location message appeared, and they waited several minutes. This rules out the known pre-map-ready path and makes a brief async delay unlikely.
- User clarified this was an emulator reproduction: its location was changed after login, and the new location was clearly different from the saved point where the picker opened. The user waited several minutes without camera movement.
- Historical diagnostics from `debug-0917-location` demonstrate a same-policy rejection example (cache 16.627 m, newer fix 21.038 m), but that measurement was on Sony XQ-AU52 and is not the current emulator run. A read-only emulator snapshot taken later showed provider fixes around 29 minutes old; it does not establish the fix age when the FAB was pressed.
- User further confirmed the main map recentered to the new simulated position after the Extended Controls change, before the picker attempt, with less than one minute between them. The main map and picker use the same location-controller implementation, weakening a provider-wide outage or long-stale-fix explanation.
- User confirmed the main map successfully recentered after the Extended Controls update and before this picker attempt. They also confirmed they did not press the picker bottom Confirm. Thus the unchanged form coordinates are expected by design; the unresolved issue is only the picker's camera not recentering.
- The user reports the blue current-location dot appeared after the picker FAB tap and clarifies it was near original point A. Alongside the main map's earlier move to B and the picker map remaining at A, this supports a stale A-near location display relative to B at ≥95% confidence. `MyLocationController` is the only app code enabling `map.isMyLocationEnabled`, and it does so only after resolving a non-null map. This confirms the click handler ran and the map object was available; those causes are excluded.
- User clarified that the underlying map did not move according to the changed coordinates. This reduces the likelihood that successful recentering merely went unnoticed. The dot was near the crosshair, but its exact coordinate relative to the map center was not captured.
- Static search finds no in-app call site for standalone, non-exported `ImportExistingWaypointActivity`; form import uses `ImportExistingWaypointBottomSheet`. That flow copies selected API latitude/longitude into the form and notifies the host. A normal form result carries the data into both the parent waypoint location and basic data; a canceled result keeps the original. Static evidence does not identify why the reported route returns A, and it may be a separate issue from camera recentering.
- Further trace: standalone `ImportExistingWaypointActivity` returns `NodeDetails` JSON but has no in-app result consumer. The in-form import BottomSheet pre-fills B into the fragment coordinate fields and emits a draft update. A return to A after that route would require a later overwrite/restoration; no such runtime event has been captured.
- A source-confirmed host-map A/B split was initially considered: host map confirmation calls `AddGutterBottomSheet.updateWaypointLocation()`, which updates `Waypoint.latLng` only. `GutterFormNavigator` passes that B location separately from still-A `basicData.NODE_X/Y`; form initialization preserves nonblank A values, and `syncCurrentWaypointFromCurrentFormData()` can overwrite B back to A. The user has confirmed B was set by importing another point, so this host-map split is ruled out as the direct incident path.
- Current classification: `implementation_regression` candidate. The stale-cache/refinement behavior introduced by `4086c3461af84a013ab65cc3567a8343be54e` remains a code-level candidate but is further weakened by the preceding main-map success through the same controller. A sanitized ADB snapshot after the report showed fresh fused/GPS fixes (age 0 s, hAcc about 4–5 m; coordinates omitted), confirming provider availability at snapshot time. Confidence in the underlying camera-recenter root cause remains below 95% because picker callback result and camera target at the reported action were not recorded. An earlier old provider snapshot was not contemporaneous and does not settle the branch. Direct ADB launch is unavailable because `MapPointPickerActivity` is non-exported; reproduction must navigate through the app.
- The current-location FAB only recenters the camera. The form coordinates are returned only by the picker’s bottom Confirm action. User confirmed they did not press Confirm, so unchanged form coordinates are expected.
- Runtime follow-up (2026-10-16): Android Studio attached successfully to the running app on the dedicated AVD. The app was on a blank new-gutter sheet, and its existing-point list/map had no candidates; entering the import route safely would require a write flow. No save/submit was performed. Callback and camera evidence remains unavailable.
- Next action: Obtain a safe existing-point form route on the dedicated AVD, then capture cached/refinement callback timestamp, age, accuracy and relative displacement, plus `onCameraMoveStarted`/`onCameraIdle` and camera target. Keep those runtime values NOT VERIFIED until captured.
