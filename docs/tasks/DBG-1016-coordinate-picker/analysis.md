# Analysis — DBG-1016 Coordinate Picker

## Reported Symptoms

1. After tapping a coordinate and changing it, the map does not move to the new location.
2. No new coordinate is obtained.

User clarified that the reported action is pressing the lower-right current-location button, and that neither the map nor its marker moved to the user's new current location. Permission was granted, the picker map was fully loaded before tapping, no unavailable-location message appeared, and the main map showed the actual location after login.

## Source Findings

- `MapPointPickerActivity` places a fixed crosshair in the center of the screen. The visible instruction says `請拖曳地圖至目標點位` (`strings.xml`, `picker_hint`).
- `MapPointPickerActivity` registers handlers for cancel, confirm, and the current-location FAB. It does not register `GoogleMap.setOnMapClickListener` or another tap-to-select handler.
- Confirm reads `googleMap.cameraPosition.target` and returns that center as `RESULT_LATITUDE` / `RESULT_LONGITUDE`.
- `GutterFormActivity.launchLocationPicker()` passes its current `NODE_Y` / `NODE_X` as the picker’s initial coordinates. `MapPointPickerActivity.onMapReady()` centers on those coordinates and only auto-requests location when both are zero. Thus a normal existing-point edit opens at the saved point, and the lower-right FAB is the action expected to recenter to the user's current location.
- `GutterFormActivity` consumes those result extras, writes `NODE_X` / `NODE_Y`, updates the form fragment and session waypoint, and animates the form map to the returned location.
- The current-location FAB requests a fused location and moves the picker camera when a usable fix arrives. The picker returns that location to the form only after the user confirms.
- The FAB rec enters the camera; it does not reposition the persisted waypoint marker. `drawExistingWaypoints()` creates those markers from the session snapshot. The selection crosshair is screen-centered. A blue My Location dot is managed by Google Maps after `isMyLocationEnabled` is set.
- If the FAB is used, location acquisition and camera movement are asynchronous. The Confirm handler remains available and immediately samples the current camera target; confirming before the location callback moves the camera can therefore return the previous target.
- If permission is denied or the location provider produces no usable fix, the picker shows the existing unavailable-location message and the camera target is unchanged.
- The picker overlay and FAB become visible during `onCreate`, before `onMapReady` assigns `googleMap`. If the FAB is tapped in that interval, `MyLocationController.enableMyLocationAndMove()` sees a null map and returns silently; the tap is dropped without requesting GPS or showing an unavailable-location message.
- `MyLocationController` accepts `lastLocation` if it is at most five minutes old and immediately moves the camera to it. It accepts the later fused refinement only if it is newer and its reported accuracy improves by at least 10 metres. The refinement policy does not compare geographic displacement. Thus a moved device's newer fix can be rejected when accuracy is equal/worse or improves by less than 10 m, leaving the map at the old cached position.
- Google Play services documents that `getCurrentLocation()` may return a recent cached fix, compute a fresh fix, or return `null` on timeout. Therefore the app's follow-up call is not guaranteed to refine the cached location. If an old cached A was accepted, a same-timestamp result, null/failed result, or rejected B result leaves the camera at A without a toast because unavailable-location callbacks run only when no cache was accepted. This is a source-supported path matching the no-move/no-toast symptoms, but its incident inputs are not recorded. ([FusedLocationProviderClient](https://developers.google.com/android/reference/com/google/android/gms/location/FusedLocationProviderClient))
- Git history shows this cached-first/refinement behavior entered the picker in `4086c3461af84a013ab65cc3567a8343be54e33e` (`fix(debug-0917-location): use cached location first`, 2026-09-18); before that commit the picker directly moved to `lastLocation` when non-null. This establishes the likely regression window, not the exact runtime branch taken.

## Initial Classification

The user clarified that this report concerns the lower-right current-location button and neither the map nor its marker reached the new current location. They confirmed location permission was granted, the picker map was fully loaded before tapping, no unavailable-location message appeared, and they waited several minutes. The emulator's location was changed after login through Android Studio Extended Controls, and the new position differed clearly from the saved point at which the picker opened. The pre-map-ready return is ruled out. The user confirmed that the main map moved to the new simulated location after the Extended Controls change, and that this successful main-map recenter occurred **before** the later picker failure, less than one minute before opening the picker and tapping its location button. Main and picker maps call the same `MyLocationController` implementation, so the emulator/provider and shared camera-centering code worked shortly before the picker attempt. This substantially weakens a provider-wide outage or long-stale-cache explanation, but does not establish that the picker tap requested a fix or what fix it received. The user also confirmed they did not press the picker bottom Confirm. Therefore the unchanged form coordinate is expected by the current contract: the location FAB only recenters the picker camera, and Confirm is the step that returns the camera center to the form. It does not explain the reported lack of camera movement.

The page source and layout show the FAB is visible and clickable, sits above the bottom action bar, and calls the location handler. The user confirms the blue Google Maps current-location dot appeared after tapping, near the fixed center crosshair and near original point A. Source search shows `MyLocationController.enableMyLocationAndMove()` is the only code that enables `map.isMyLocationEnabled`, and it does so only after obtaining a non-null map from `mapProvider()`. This is strong runtime evidence that the FAB click handler ran and the picker map object existed; missed-tap and null-map hypotheses are excluded for this run. The user has now clarified that the underlying map did not move according to the changed coordinates, reducing the likelihood that camera movement succeeded but went unnoticed. The user places the dot near original point A, while the main map had moved to B less than one minute earlier. The function requests cached and high-accuracy fixes asynchronously. With no unavailable-location message, remaining explanations include a cached location near the old center followed by a rejected refinement, a location request that remained pending, or accepted fix followed by a camera operation that did not complete. The main-map recenter less than one minute earlier further weakens a stale/old fix, but picker callback and camera events were not captured. An earlier read-only emulator snapshot showed provider fixes around 29 minutes old; a later sanitized snapshot showed fresh fused/GPS fixes (age 0.0 s at snapshot, hAcc about 4–5 m). Neither was captured at the picker request. A direct ADB launch cannot reproduce the picker because Android rejects the non-exported `MapPointPickerActivity`; reproduction must enter through the app flow. The stale A-near location display relative to B is supported at **at least 95% confidence**. Confidence in the underlying camera-recenter root cause remains **below 95%**, and its exact cause is NOT VERIFIED.

No production code was changed during this analysis.

## A-to-B Import Return Path

The user confirms B was chosen by importing another existing point. This is distinct from the lower-right location FAB failure. The user's earlier component name `ImportExistingWaypointActivity.kt` does not match the production flow found on this branch: repository search finds no app launcher for that standalone, non-exported Activity. `GutterFormActivity.showImportExistingWaypointSheet()` opens `ImportExistingWaypointBottomSheet`, and its `onImport` callback calls `handleImportedNodeDetails()`.

The live import path writes the selected API latitude/longitude into `GutterBasicInfoFragment.coordXValue/coordYValue`, then calls `notifyDraftChanged()`. `GutterFormActivity.onBasicInfoDraftChanged()` merges this data into `currentFormData`; `syncCurrentWaypointFromCurrentFormData()` updates the in-memory session waypoint. On normal form completion, `resolveEffectiveCoordinates()` prefers valid `NODE_Y/NODE_X` from this data, and the parent result handler updates both the waypoint map location and `basicData`. Source therefore predicts B in the returned model after `RESULT_OK`.

The import draft callback itself does not update `currentLat/currentLng`, move the form map camera, or rerender session markers. However, selecting a candidate has its own callback: `ImportExistingWaypointBottomSheet.onSelected()` calls `showImportSelectedWaypoint()`, which animates the form map to the candidate's parsed latitude/longitude. Dismissing the sheet clears temporary markers and resets map padding but does not explicitly move the camera back to A. The user confirms the viewport stayed at A **after selecting B and before pressing Import**. This excludes a return-time camera reset as the explanation for that observation: the expected selection-time pan did not visibly happen. The user is unsure whether a B highlight appeared. The user confirms the three-tab half-height sheet was used: Recent Access works, while Nearby alone shows `無資料` and does not update to B. Source renders `無資料` only after a successful response whose `data` is null/empty; request/API errors and location errors have distinct messages. This makes a successful empty response highly likely, but does not establish whether the request used B's coordinates or whether the backend should return a point at that location. The separately declared `ImportExistingWaypointActivity` has no production caller in the current repository.

If the user means that coordinate data is A after closing and reopening the form, the normal `RESULT_OK` implementation does not explain it: it should return B. The user clarified that system Back showed `尚未填寫完畢`, then they pressed `確認` and returned to `AddGutterBottomSheet`; source maps this to `RESULT_OK`, so a canceled result is not a fit for the reported path. The user does not remember whether form coordinates showed A or B before leaving. Current emulator logcat contains no import/result trace for the reported sequence. CUA currently reports the Mac locked, so the remaining form fields, result extras, and parent camera target cannot be captured until the user unlocks. No production code was changed.
